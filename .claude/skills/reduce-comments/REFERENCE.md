# reduce-comments: classification reference

The test for every comment:

> Does this tell me something the code cannot?

Yes: **Keep**. Yes, but at four times the needed length: **Simplify**. No: **Remove**. Unsure: **Keep**. A wrongly
kept comment costs a line; a wrongly deleted one destroys the only record of a decision.

## Remove

A comment that restates the statement below it, names the obvious, or labels a block with a word already in the code.

```csharp
// Set the user id
userId = request.UserId;

// Return the result
return result;

// Constructor
public SmsGatewayClient(HttpClient http) { }
```

Also remove:

- **Commented-out code.** Git keeps it. Exception: it sits next to an explanation of why it is disabled
  (`// Disabled until the gateway profile ships, see ADR-011`); keep both.
- **Empty banners** (`// ---------`) that separate nothing. A banner that names a real section is navigation: keep.
- **Stale scaffolding**: `// TODO: implement` above an implemented method, `// Add your code here`.
- **Changelog lines**: `// Modified by X on 12/03`, `// v2 - fixed bug`. Git owns history.

## Simplify

True and worth having, but one sentence of signal buried in a paragraph:

```csharp
// This method is responsible for sending the message through the integration gateway by first
// requesting a signed service token from the token endpoint and then calling the SMS endpoint
// with that token in the authorization header.
```

becomes

```csharp
// The gateway rejects an SMS call without a fresh service token from its token endpoint.
```

- Keep every **fact**; drop every **restatement of structure** (the call order is visible in the body).
- Never invent a justification you have not verified. If you cannot confirm a claim, keep the comment verbatim.
- Preserve identifiers, error codes, ADR numbers, ticket ids and links exactly. Keep every caveat.

## Keep

Anything that answers **why**:

| Category | Example |
| --- | --- |
| External API requirement | `// The directory matches on the login name AND the organization unit together.` |
| Business rule | `// A rejected request may be resubmitted once; the second rejection is final.` |
| Security | `// Never log the response body: it carries the applicant's national id.` |
| Non-obvious decision | `// Classifier order is a contract: Concurrency must precede TransientFault.` |
| Workaround | `// SQL Server returns 0 rows here when MARS is on; count separately.` |
| Performance | `// Cached for the process lifetime: the dataset never changes within a run.` |
| Known limitation | `// Cannot tell a mismatch from an outage until the provider documents its codes.` |
| Contract with a test | `// Asserted in OutboxDrainTests; keep the two in step.` |
| Why not | `// Deliberately not UseForwardedHeaders: that rewrites the address pipeline-wide.` |

The last row matters most: a comment explaining a road **not** taken cannot be rebuilt from the code.

Treat as Keep on sight: ADR references (`ADR-004`), error codes (the values of `<Name>ErrorCodes`), permission keys,
analyzer and rule ids (`CLB1004`, `RS0030`), use-case and business-rule ids from the project's requirement documents
(`UC-12`, `BR-3`), "asserted in `...Tests`", and any comment explaining a retired or reserved value (why an enum value
or lookup id is never reused).

## Never remove

- `TODO`, `FIXME`, `HACK`, `XXX`, `WARNING`, `SECURITY`, `IMPORTANT`, `NOTE:`, `CAUTION`, `BUG`.
- Licence and copyright headers; generated-code markers (`<auto-generated>`, `DO NOT EDIT`, EF migration
  `/// <inheritdoc />`).
- Tool directives, which are syntax rather than prose: `#pragma warning disable/restore`,
  `// eslint-disable-next-line`, `// @ts-ignore`, `// @ts-expect-error`, `// prettier-ignore`, `/// <reference ...>`,
  `// stylelint-disable`, `-- noqa`.
- `#region` / `#endregion` and `#if` / `#endif` (code, not comments).

## XML doc and JSDoc

`///`, `/** */` and `<summary>` blocks are public API documentation; they feed IntelliSense and doc generation.

- Never delete one in the automatic pass. An empty one or a pure tautology (`/// <summary>Gets or sets the
  Name.</summary>` on `Name`) may be listed in the report as a suggestion; leave it in the file.
- Never delete `<param>`, `<returns>`, `<exception>` or `<inheritdoc />`: with documentation warnings on, removing
  them changes the build.
- Simplify one only when it is verbose prose and no tag is lost.

## Per language

- **C#**: `///` is doc, `//` and `/* */` are prose. Watch for `//` inside verbatim (`@"..."`), interpolated
  (`$"..."`) and raw (`"""..."""`) strings.
- **TypeScript / JavaScript**: `/** */` above an export is API documentation. `//` inside a template literal, a URL
  string or a regex literal is not a comment.
- **Angular templates**: `<!-- -->` comments; one explaining why a control is conditionally rendered is a
  high-value keep.
- **SQL (T-SQL)**: `--` and `/* */` (block comments nest). Keep anything explaining an index, a hint, an isolation
  level, a locking choice or a migration's data transformation and irreversibility. `'a--b'` is a string and
  `[we--ird]` an identifier.

## The differ

```text
node .claude/skills/reduce-comments/scripts/comment-diff.mjs count  <file> [<file> ...] [--json] [--dialect <d>]
node .claude/skills/reduce-comments/scripts/comment-diff.mjs verify <baseline> <edited> [--json] [--dialect <d>]
```

Exit codes: `0` comments only (or counted), `1` code changed, `2` usage, unreadable or unsupported file.

| Dialect | File extensions | Comments | Literals kept verbatim |
| --- | --- | --- | --- |
| `csharp` | cs, csx | `//` `///` `/* */` | `"..."`, `@"..."`, `$"..."` (holes scanned), `$@`/`@$`, raw `"""..."""` and `$$"""`, char `'x'` |
| `script` | ts, mts, cts, js, mjs, cjs | `//` `/* */` `/** */` | `'...'`, `"..."`, template literals (holes scanned), regex literals |
| `html` | html, htm | `<!-- -->` | quoted attribute values, quoted strings in `{{ }}`; script, style, textarea and title bodies are code |
| `sql` | sql | `--` and nested `/* */` | `'...'` (`''` escape, `N'...'`), `"ident"`, `[ident]` (`]]` escape) |

The dialect comes from the edited file's extension, else the baseline's; `--dialect` overrides both.

**What is compared.** Comments are dropped and act as whitespace: a line break when the comment spans lines,
otherwise a space. Code whitespace runs collapse to one space, or one line break when the run holds one. Literals are
kept byte for byte. So re-indenting a line passes, while joining two lines, changing a string's spacing, or deleting
a comment that separated two tokens (`a/**/b` to `ab`) fails.

**`count`** reports comment units: a run of whole-line single-line comments of the same flavour on consecutive lines
is one unit, a block comment is one, a trailing comment is one. Report these, not raw line counts.

**Known limits.** All but the last fail safe, as a false alarm:

- TSX and JSX files are not supported (`//` inside JSX text is text); exit 2.
- A comment inside a C# interpolation hole or a template literal `${}` hole is part of the literal: editing it
  fails.
- A `<!--` inside an Angular `{{ }}` expression or a control-flow condition is code.
- A `/` after `)` or `]` is read as division, after `}` or an operator as a regex. A regex literal placed directly
  after `)` (`if (ok) /a\/*b/.test(s)`) is therefore read as code, and a `//` or `/*` inside it would be taken for a
  comment. This is the one shape that could hide a change: if the target holds a regex literal right after `)` that
  contains `//` or `/*`, check that line in `git diff` by eye and say so in the report.
