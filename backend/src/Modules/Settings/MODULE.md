# Settings module

## Purpose

Runtime settings (module 6a): values an administrator changes without a deployment, visible on every API node. It
replaces the old pattern of a static value that only the node handling the admin request updated. The module owns:

- **`settings.Settings`**: one row per setting: `Key` (primary key, `<group>.<kebab-name>`), `Group`, `ValueType`
  (`SettingValueType`, stored as int: `Text = 1`, `WholeNumber = 2`, `Boolean = 3`, `DurationSeconds = 4`), `Value`,
  `DefaultValue`, `DescriptionAr`, `DescriptionEn`, optional `MinValue`/`MaxValue` (numbers only, server-side), and
  `UpdatedAt`/`UpdatedByUserId` (null until an administrator changes it).
- **`settings.SettingsStamp`**: a single row (`Id = 1`) with a `bigint Version`, incremented in the same transaction as
  every settings change.
- **The scoped `IRuntimeSettings` reader** (kernel port in `Starter.Application.Settings`) over a node-wide snapshot.
- **The admin endpoints** to list settings and change a value.

## Use

Read a setting from any module through the kernel port; never reference this module:

```csharp
public sealed class ListNotifications(IRuntimeSettings settings, ...)
{
    var pageSize = settings.GetInt32(SettingKeys.NotificationsPageSize);
}
```

`GetString`, `GetInt32`, `GetBoolean` and `GetDuration` throw `InvalidOperationException` for an unknown key or a
type mismatch: both are programming errors (the key constant and the migration disagree). Read on every use; never
copy a value into a static or a singleton field.

Seeded settings (`SettingKeys`) and their consumers:

| Key | Type, range, default | Read by |
| --- | --- | --- |
| `portal.contact-enabled` | boolean, true | Portal `SubmitContactMessage`: false refuses the public form with 409 `PORTAL_CONTACT_DISABLED` |
| `notifications.page-size` | integer, 5-100, 20 | Notifications `GetNotificationFeed`: the page size of a feed request without `take` (capped at 50) |
| `session.idle-warning-minutes` | integer, 1-240, 15 | not read yet: the web app still uses its own constant (follow-up: a read endpoint for the SPA) |

Seed a setting only together with its consumer; a seeded key nothing reads promises the administrator a behaviour
that does not exist. (`notifications.retry-delay` was dropped for that reason: the outbox back-off is the kernel's
`OutboxDrainSchedule`, one schedule for every message type.)

| Endpoint | Permission | Body / answer |
| --- | --- | --- |
| `GET /api/admin/settings` | `settings.view` | `[{key, group, valueType:int, value, defaultValue, descriptionAr, descriptionEn, updatedAt: string\|null}]`, by group then key |
| `PUT /api/admin/settings/{key}` | `settings.manage` | body `{value: string}` -> 200 the setting; 400 problem+json with field `value` (`REQUIRED`, `TOO_LONG`, `INVALID_FORMAT`, `SETTINGS_VALUE_OUT_OF_RANGE`); 404 `SETTINGS_SETTING_NOT_FOUND` |

Value formats (`Domain/SettingValueFormat`, the only owner): integers in invariant culture with an optional sign;
booleans `true`/`false` in any case, stored lower-case; durations as whole non-negative seconds; text as given (may be
empty). Values are at most 2000 characters. An update to the same canonical value writes nothing.

Configuration: `Settings:CheckStampPerScope` (default `true`).

## Extend

- **Add a setting:** add a key constant (`SettingKeys` for a platform setting, or `<Module>SettingKeys` in the owning
  module), then a NEW Settings migration that inserts its row (copy the `InsertData` loop of `InitialCreate` with a
  frozen seed list of its own). Never edit `SettingsSeed` or `InitialCreate` once shipped, and never insert rows at
  runtime. Add the ar/en descriptions in the row itself.
- **Change a setting's type, range or remove it:** a new migration that updates or deletes the row, together with the
  code that reads it.
- **New permission:** `node tools/scaffold/new-permission.mjs --module Settings --action <kebab>`.

## Rules

- Rows are created, changed structurally and removed only by migrations; the admin endpoint changes values only.
- Every write goes through `ISettingsUnitOfWork.SaveChangesAndAdvanceStampAsync` (value and stamp in one transaction).
- Values are parsed and written only by `SettingValueFormat`.
- The module never references another module; the acting user comes from the kernel `ICurrentUserContext` and
  `IUserDirectory` ports.
- Every use case, validator and domain rule has unit tests in `backend/tests/Modules/Starter.Modules.Settings.Tests`.
- `module.rules.yaml` holds the module rules; `CLAUDE.md`, `BannedSymbols.generated.txt`, `.editorconfig` and
  `CodeMetricsConfig.txt` are generated by `node tools/rules-engine/compile.mjs`.

## Gotchas

- **Freshness bound: 30 s.** `SettingsLimits.CacheTtl` (30 s, from the injected `TimeProvider`): a snapshot that old is
  reloaded on the next read, even inside a scope that already checked the stamp. With the per-scope stamp check on
  (default), the first read of each request runs one single-row query and reloads when the version differs, so other
  nodes normally see a change on their next request. With `Settings:CheckStampPerScope=false`, they see it within 30 s.
- A snapshot expires at exactly 30 s (`now - loadedAt >= CacheTtl`).
- The reads are synchronous (the port is synchronous); the stamp query or reload runs at most once per scope and per TTL.
- The node that made the change drops its own snapshot right away; a slow load never replaces a newer snapshot.
- Tests and integration hosts: `SettingsSnapshotCache` and `TimeProvider` are registered with TryAdd, so a test host can
  register its own (for example two TestServer hosts on one database, each with a `FakeTimeProvider`).
- The key column uses the database collation; the admin lookup still matches keys ordinally (case-sensitive).
- Changes are audited by the kernel audit interceptor (the stamp increment uses `ExecuteUpdate` and is not audited).
