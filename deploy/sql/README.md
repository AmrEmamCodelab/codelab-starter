# deploy/sql

DBA scripts. The API never migrates a server database itself (`Database:ApplyMigrationsOnStartup` is refused
outside Development), so every release that changes a schema ships its migrations as SQL files a DBA reviews and
runs.

| What | Where |
| --- | --- |
| The release's migration scripts, one per DbContext (`NN-<Context>.sql`) and `sql-scripts.json` | the deploy kit's `sql\` folder (`publish/deploy-<shortsha>/sql`), generated by [tools/sql-kit/New-DbaSqlScripts.ps1](../../tools/sql-kit/New-DbaSqlScripts.ps1) |
| Audit append-only grants | [audit/](audit/README.md) |

The generated files are never committed: they belong to one release and are rebuilt from the migrations in the code.

## How the scripts are made

`New-DbaSqlScripts.ps1` builds the API host, asks EF Core for every DbContext the host registers, and runs
`dotnet ef migrations script --idempotent` for each (no database is opened). It then reshapes each script
([tools/sql-kit/MODULE.md](../../tools/sql-kit/MODULE.md)):

- Every step keeps EF's guard (`IF NOT EXISTS (... [MigrationId] = N'...')`), and its body runs through
  `EXEC(N'...')` in a batch of its own (`GO` after it, quotes doubled). A step that is already applied is never
  compiled against the current schema, so a file runs on a database at **any** earlier state, and a rerun does
  nothing.
- Each migration is one transaction. With `SET XACT_ABORT ON` and `:on error exit`, a failing step rolls its migration
  back and stops the run; the migrations before it stay applied, and the next run continues from the failed one.
- A prologue refuses to execute anything outside **SQLCMD mode** and sets the session options SQL Server needs for
  filtered indexes and computed columns (`QUOTED_IDENTIFIER ON` and the rest; sqlcmd starts with it off).
- Files are numbered in the order the API applies migrations: the kernel contexts (audit, outbox, numbering), then the
  modules by name. Each context owns its schema and its own `<schema>.__EFMigrationsHistory`.

```powershell
# Generate (a developer or the kit build; needs dotnet-ef 10 via -EfToolPath, CODELAB_DOTNET_EF or PATH)
powershell -NoProfile -ExecutionPolicy Bypass -File tools\sql-kit\New-DbaSqlScripts.ps1 -OutputPath <empty folder>
```

## DBA flow (each release)

1. **Back up** the application database.
2. **Read** the files. `sql-scripts.json` lists every file with its context and migration ids; each file's header
   lists its migrations too. Only migrations missing from a context's history table will run.
3. **Run every file in order**, in SQLCMD mode, with a login that may create schemas and tables (never the
   application's login):

   ```powershell
   Get-ChildItem <kit>\sql\*.sql | Sort-Object Name | ForEach-Object {
       sqlcmd -S <server> -d <database> -E -b -f 65001 -i $_.FullName
       if ($LASTEXITCODE -ne 0) { throw "$($_.Name) failed; fix the cause and run the files again from this one." }
   }
   ```

   In SSMS: open a file, **Query > SQLCMD Mode**, select the database, Execute; then the next file. `-f 65001` (or
   SSMS with the file's BOM) keeps Arabic seed text intact.
4. **Check** that each file ends with `<Context>: migrations are up to date.`
5. **Then** update the API servers with the kit (`Install-Api.ps1`). Run [audit/Grant-AuditAppendOnly.sql](audit/Grant-AuditAppendOnly.sql)
   again when the release adds a record history table.

A failed file stops at the failing step; nothing of that migration remains. Fix the cause (for example a duplicate
row a new unique index refuses) and run the same files again: the applied migrations are skipped.

## Rules

- Never edit a generated file. A wrong script is a wrong migration: fix the migration in the code and regenerate.
- The application login is not `db_owner`: the DBA's login applies schema changes.
- No hosts, logins or database names in this folder.

## Gotchas

- **Without SQLCMD mode nothing runs.** SSMS in normal mode fails the `:setvar` line and the guard turns execution off
  (`SET NOEXEC ON`) for the rest of the file, printing a message. Switch the mode on and run the file again.
- **`$(` is reserved.** sqlcmd substitutes `$(name)` everywhere, string literals included; the reshaper refuses a
  migration whose SQL contains it.
- **Schemas outside EF.** The job server's schema (`Jobs:PrepareSchemaIfNecessary`) and the security stores
  (`Codelab:Security:SqlStore:EnsureSchemaOnStart`) are created by the API at start, not by these files. Either give
  the application login the rights for that first start, or let the DBA run a first start with an elevated login and
  then switch the setting off.
